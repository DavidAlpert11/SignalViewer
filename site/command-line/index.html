    Command line, Python and file formats¶

    Everything here works without the window, on a PC without a screen and in CI. signalviewer-cli is installed by pip install signalviewer; from the source folder it is python cli.py.

    Read and export¶

    signalviewer-cli info flight.bin                       # the signals, their samples and time span
signalviewer-cli export flight.bin --signals "ATT.Roll,ATT.Pitch" --out roll.csv --t0 10 --t1 60
signalviewer-cli export run.csv --out run.mat           # one MATLAB variable per signal + Time

    Signal names may be written without their unit and in any case (ATT.Roll for ATT.Roll [deg]) when that is one signal; a name that is not there gets the closest names.

    Reports¶

    signalviewer-cli report --template "ArduPilot · Full review" --out reports/ logs/*.bin --format pdf
signalviewer-cli templates                              # what --template can name

    Disk space: cache¶

    signalviewer-cli cache                      # the CSV cache and log indexes, dropped-file copies, map tiles: size and folder
signalviewer-cli cache --clear all          # or: cache / uploads / tiles - with the app closed

    The app keeps the cache small by itself (an old copy of a changed file is removed, entries unused for 30 days go, at most 5 GB: SV_CACHE_MAX_GB, SV_CACHE_DAYS); Settings shows and clears it too. SV_LAZY_MB (default 1536) is the memory big logs' values may use before the least recently used are read again from the file. SV_OPEN_BUDGET_MB (default half the computer's memory, at most 8 GB) is the memory files opened together may use while they are read side by side. SV_MEMCACHE_MB (default 1024) is the memory for results that can be computed again (changed and derived signals, spectra, plot summaries, statistics): beyond it the least recently used go, and are computed again when needed.

    Pass / fail in CI: check¶

    signalviewer-cli check runs/*.csv --checks checks.json --junit results.xml
signalviewer-cli check flight.bin --template "My limits"   # the limits saved on signals in the app

    A checks file (example):

    {"checks": [
  {"name": "Engine temperature below 88 °C", "signal": "EngineTemp", "hi": 88},
  {"name": "Speed while cruising", "signal": "Speed", "lo": 20, "hi": 76,
   "during": {"state": "DriveMode", "value": "CRUISE", "occurrence": "all"}},
  {"signal": "RPM", "lo": 1000, "hi": 3000, "t0": 5, "t1": 50, "scale": 1, "offset": 0}
]}

    during.occurrence: 1 = the first stretch of the state, 2 = the second…, -1 = the last, left out = all. Each failure says how many times the signal left its limits, when first, and the worst point. Exit code 0 all passed, 1 a check failed, 2 a check could not be made (a missing file, signal or state value - never a silent pass). --junit writes results CI systems show as tests.

    A test-bench example (examples/bench, also a card on the welcome screen): a pump run recorded as Parquet - phases as a state (Phase), units, a 0.2 s pressure spike, a 2 s gap and a motor temperature that creeps over its limit - with its checks.json (one check only while the state is STEADY):

    signalviewer-cli check examples/bench/pump_run_07.parquet --checks examples/bench/checks.json

      FAIL  Motor temperature below 85 °C  - MotorTemp [°C]: 30 time(s) outside, first at 545.980 s; worst 1.277 above hi at 559.740 s
  FAIL  Pressure below 16 bar  - Pressure [bar]: 1 time(s) outside, first at 412.000 s; worst 5 above hi at 412.000 s
  PASS  Speed 2850 - 2950 rpm while steady
  PASS  Vibration below 0.5 g
2 passed, 2 failed, 0 errors, 0 skipped

    2 of the 4 checks fail on purpose, so the exit code is 1 - the way a CI job fails. In the app the same file is read in Checks: the verdict and the data quality (the gap) as cards.

    Against a golden run: compare¶

    signalviewer-cli compare golden.csv new/*.csv --tol-pct 2
signalviewer-cli compare golden.bin today.bin --tolerances tol.json --junit compare.xml

    {"default": {"abs": 0.5}, "signals": {"Speed": {"abs": 1.0}, "RPM": {"pct": 3, "outside_pct": 1}, "Gear": {"skip": true}}}

    The app writes this file too: Compare runs ▸ Tolerance and alignment ▸ Save tolerances… (each signal's own tolerance is set under it in the panel), and opens it again with Open tolerances….

    Every signal both runs have, with the Compare panel's numbers (RMS and largest difference, correlation; headings wrap at 360°), the most different first. A signal passes when every sample is within the larger of abs and pct of the golden value (as the Simulink Data Inspector; before 1.21 the smaller, which failed every zero crossing of a signal with pct - give abs too for a signal that crosses 0) - or, with "outside_pct" (--allow-outside PCT for every signal), when no more than that share of its samples is outside. --tol-time SECONDS (or "time" in the tolerances) lets a run be that much early or late: the golden value's band at each moment is its lowest and highest value within ± that time, then widened by abs / pct - as the Simulink Data Inspector. Without any tolerance the differences are only listed.

    Every sample counts (since 1.23): pass / fail, the share outside and the largest difference are judged on all the samples of both runs inside their overlap - the run's own samples against the golden curve there, and the golden samples against the run - so a 5 ms excursion in two million samples, or a violation between two samples of a 10 Hz golden run recorded at 1 kHz, fails. The share outside is counted over those samples (the union of both runs' sample times). The Compare panel judges the same way, so the app and the command line give the same verdict.

    A simulation against a flight¶

    Two loggers, two clocks, two naming habits: --align auto lines the run up with the golden run by cross-correlation (--align-on NAME to choose the signal, --align SECONDS to give the shift), names match with or without their unit, and {"as": "name in the run"} in the tolerances pairs signals named differently. A worked example: Simulation against flight.

    A run envelope's results: sweep¶

    signalviewer-cli sweep results.csv --question question.json         # how many sets hold, the best five
signalviewer-cli sweep results/ --question study.svsweep --top 10   # a folder of tables; a study saved by the app
signalviewer-cli sweep results.csv --question q.json --min-holding 3 --json

    {"conditions": [{"column": "roll_error_deg", "op": "<=", "value": 5, "mode": "all"},
                {"column": "overshoot_pct", "op": "<=", "value": 15, "mode": "all"}],
 "combine": "and", "goal": {"column": "energy_wh", "direction": "min"}}

    The table has a row per run (CSV, Parquet or Excel, or a folder of them); the columns' roles are guessed as in the app's Sweeps area, and a study saved there (.svsweep) brings its own roles and goal. The answer is the app's: how many parameter sets meet every condition in every must-hold-across combination, and the best of them. On the bundled example (examples/sweeps/drone_tuning.csv):

    12 of 45 parameter sets hold in all 18 combinations (0 miss a combination)
  roll_error_deg <= 5: met by 27
  overshoot_pct <= 15: met by 28
  1. kp_roll=0.2, ki_roll=0.02, filter_hz=10, goal=47.86

    Exit code 0 = at least --min-holding sets hold (default 1), 1 = fewer, 2 = the table or the question cannot be read - so a CI job fails when a change leaves no tuning that works everywhere.

    Numerical validation: validate¶

    signalviewer-cli validate                   # one line per case, then "23 passed, 0 failed"
signalviewer-cli validate --json            # every case with expected, measured, error, tolerance
signalviewer-cli validate --junit v.xml     # JUnit XML, e.g. as a record that this installation computes correctly

    Spectra, filters, derivative and integral, statistics, decimation, Compare and coordinate frames, each against a reference that does not come from the app. Exit code 0 = every case within its tolerance, 1 = one is not. The cases and the conventions behind them: Validation.

    Map objects: objects, compare-objects, compare-similar, map¶

    The objects a file holds - found by their names with the app's rules (one table, backend/svcore/object_names.json) - and their comparison, with the same numbers as the app's Compare objects… dialog. The whole process with Python, the command line and REST, step by step: API.

    signalviewer-cli objects flight.bin                 # POS: navigation (POS), LLA ... XKF1[1]: NED, origin ORGN[0] (known)
signalviewer-cli objects flight.bin --all --json    # also what Add all would not add; the reasons as data
signalviewer-cli compare-objects flight.bin --ref POS --objects "XKF1[0],XKF1[1]" \
    --what position,velocity,attitude --frame ned \
    --csv errors.csv --stats stats.csv --map map.png --map-html map.html --report report.html
signalviewer-cli compare-objects flight.bin --ref POS --tolerance position=2m,attitude=1deg --junit r.xml   # CI
signalviewer-cli compare-objects truth.csv flight.bin --ref truth:phys --objects POS   # two files
signalviewer-cli compare-similar flight.bin --leaf Yaw --ref "XKF1[0]" --csv yaw.csv   # nav1 / nav2, XKF1[0] / XKF1[1]
signalviewer-cli map flight.bin --out map.html      # the offline map page (or .png / .svg)

    compare-objects: --frame is ned, enu, ecef, lla (north / east / up) or track (along / cross / up). Each object's errors against the reference: the differences per component, the horizontal / vertical / 3D error, the velocity differences and the speed error, the roll / pitch / yaw errors (yaw wrapped to ±180°), and their statistics on the full data (RMS, mean, largest |error| and when, 95th percentile). Quantities that cannot be compared (no velocity, no attitude of its own) are left out and named. With --tolerance, every error component of a quantity must stay within it (its largest |error|): exit code 0 = all within, 1 = one is not, 2 = it could not be compared; --junit writes one test case per object and quantity.

    Several files: the objects of each, an object named file:name where two files share a name; each on its own recorded time (no offset), the compared object read onto the reference's samples (linear) - as the app.

    Python¶

    import signalviewer as sv
rec = sv.load("flight.bin")
t, roll = rec.signal("ATT.Roll")
df = rec.to_dataframe(["ATT.Roll", "ATT.Pitch"], t0=10, t1=60)     # one time base
sv.show(t, {"roll x2": 2 * roll}, name="from my notebook")         # into the open app

rec.objects()                                    # the map objects: name, class, frame, origin, why
nav = rec.object("XKF1[0]")                      # t, lat, lon, alt (NED placed on Earth), roll, pitch, yaw, vn, ve, vd
cmp = sv.compare_objects(rec, reference="POS", objects=["XKF1[0]", "XKF1[1]"], what=("position", "attitude"))
cmp.stats()                                      # object x component -> rms, mean, max_abs, p95_abs, t_max_abs
cmp.errors(); cmp.values(); cmp.to_csv("errors.csv"); cmp.to_mat("errors.mat")
sv.similar(rec)                                  # families of similar signals
sv.compare_signals(rec, ["XKF1[1].Yaw [deg]"], reference="XKF1[0].Yaw [deg]")   # angles wrapped
sv.map_image(rec, path="map.png"); sv.map_html(rec, path="map.html")
sv.report(rec, "report.pdf", compare=cmp)        # the map, the error plots, the statistics table

    Your own formats¶

    signalviewer-cli readers shows the readers folder (~/.signalviewer/readers) and what is in it; readers --example writes a Python reader to start from:

    @reader(extensions=[".kv"], name="key=value lines")
def read_kv(path):
    ...
    return {"time": t, "signals": {"speed": speed, "mode": codes}, "labels": {"mode": {0: "IDLE", 1: "RUN"}}}

    Return one time for all signals, or a tuple (time, values) for a signal with its own time, or None for "not my file". Saving the file is enough - no restart.

    Raw binary packets (ICD layouts)¶

    A <name>.icd.json in the readers folder describes packets as they come off the wire; files with its extensions then open as signals <packet>.<field> [unit]. Try it with signalviewer-cli readers --example-icd run.tlm (a layout and a recording).

    {"name": "Bench telemetry", "extensions": [".tlm"], "byte_order": "little",
 "header": {"sync": "0xA55A", "size": 4, "id": {"offset": 2, "type": "u8"}, "length": {"offset": 3, "type": "u8"}},
 "packets": [{"id": 1, "name": "NAV", "size": 14, "time": "t_us", "time_scale": 1e-6, "fields": [
   {"name": "t_us", "offset": 0, "type": "u32"},
   {"name": "alt", "offset": 4, "type": "i32", "scale": 0.01, "unit": "m"},
   {"name": "mode", "offset": 10, "type": "u8", "enum": {"0": "IDLE", "1": "CLIMB", "2": "CRUISE"}},
   {"name": "armed", "offset": 11, "type": "u8", "bits": [0, 1]},
   {"name": "volt", "offset": 12, "type": "u16", "scale": 0.001, "unit": "V", "byte_order": "big"}]}]}

    Types u8 i8 u16 i16 u32 i32 u64 i64 f32 f64; value = raw × scale + offset_value. Time from a packet's field, else from the header ("time": {"offset", "type", "scale"}), else the packets are numbered. Noise, unknown ids and a cut-off end are skipped to the next sync and counted in the load report. YAML layouts (.icd.yaml) work when PyYAML is installed.

    CAN bus logs¶

    candump logs (.log), Vector ASC (.asc) and CAN frame tables (.csv with time, id and data columns) open with every .dbc next to the log or in the readers folder. Signals are named <Message>.<Signal> [unit], each message at its own rate; value names become text values. Multiplexed signals, float signals, 29-bit ids and CAN FD payloads are decoded; frames whose id is in no .dbc are counted in the load report.

    With pip: full or light¶

    pip install signalviewer has everything. pip install signalviewer-lite is the core (CSV, MATLAB v5, ArduPilot .bin, CAN, binary layouts, every plot and analysis, HTML reports); its extras: [parquet] [hdf5] (.h5, MATLAB v7.3) [mavlink] (.tlog, live) [px4] (.ulg) [ros] (.mcap) [reports] (PDF, Word, images) [desktop] - or [all]. A file that needs a missing extra says which. Install one of the two packages, not both (they install the same signalviewer module).
