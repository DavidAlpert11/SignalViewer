Spec: `docs/dev/AGENT_PROMPT_2026-11-14.md`. Base: `main` at `44f97e5` (1.27.0 final, not tagged). **Phase 1 only:
no product code is changed until the owner approves this plan.** Pictures: `docs/dev/mockups/` (open

## 0. In one page

- **Sweeps (the main problem).** Today the area shows *either* the single-table study (`StudyView`, store
  `useSweeps`, file `.svsweep`) *or* Common parameters / the loop / the demo (`StudyPanel`, store `useStudyPanel`,
  file `.svstudy.json`) – two stores, two files, two Undo histories, two sets of charts. The tables the loop and
  the demo write (`next/round_k/collected_<table>.csv`) are never offered to the single-table tools.
  **Recommendation (option A, §4.3):** one Sweeps workspace – a left *study navigator* (what is shared: Common
  parameters and the loop; each table with its rounds; merged tables), the chosen table's four steps in the middle
  (the same tools as today), and the loop with the shared answer in a right column that stays in sight.
  One study model, one store, one Undo; `.svstudy.json` is the study file (with an optional `workspace` block for
  the per-table questions), `.svsweep` keeps opening and saving as a one-table study.
- **The look.** ArduDeck's public screenshots show a few principles worth taking (a darker canvas so the data
  carries the colour, chart cards with a small-caps head and their own actions, a mode band above the lines, quick
  filter chips over a coloured field list, status cards tinted by severity, big tabular numbers): §3. They become
  Signal Viewer's own tokens and components (§5) – not its branding, icons or screens.
- **Every feature stays.** §2.2 is the acceptance checklist (every capability and where it is today → where it goes).
- **Order of work:** A tokens + components → C Sweeps unification → B plots → D every area → E docs and release
  (§7; C before B because Sweeps is the owner's main complaint and is structural, B is visual).
- **What the owner decides:** §8 (eight questions, each with a recommendation).

## 3. Research – ArduDeck and three other tools

### 3.1 ArduDeck – what could be confirmed

Sources (read 2026-11-14): the site <https://ardudeck.com/>, its screenshots page <https://ardudeck.com/screenshots/>,
the blog post <https://ardudeck.com/blog/introducing-ardudeck-ground-control-station/>, the repository
<https://github.com/rubenCodeforges/ardudeck> (README, root `package.json`), the ArduPilot forum thread
<https://discuss.ardupilot.org/t/welcome-to-ardudeck-a-modern-ground-control-station-for-ardupilot/144390>, ArduPilot's
GCS list <https://ardupilot.org/copter/docs/common-choosing-a-ground-station.html>. Three screenshots were looked at
directly: `flight_log_explorer.jpg`, `telemetry_tactical.jpg`, `flight_log_health.jpg` (under
`https://ardudeck.com/images/`; not copied into this repository).

What the pages say: a ground control station for ArduPilot, iNav and Betaflight (Electron, React 18, TypeScript,
Vite, Zustand; *"The UI is Tailwind CSS, dark theme"*); a dashboard of *"IDE-style panels with saveable layouts"*; 30+
map instruments in *"analog, numeric and compact variants"*; a Log Explorer with *"multi-chart plotting … independent
y-axes, zoom/pan, windowed min/avg/max stats, and synchronized cursors across charts, map, and 3D flight path"*; health
reports with pass / warn / fail checks; a field picker. Beta (versions on the pages disagree: 0.1.x / "Beta 1.2").

What the screenshots show (observed, described in words):
1. **A darker, cooler canvas** (near-black navy) with panels one step lighter and 1 px borders; the plots' backgrounds
   are the darkest surface, so saturated series stand out. A light theme exists for the telemetry view.
2. **Chart cards with a head of their own**: a tab-like title with ×, a small-caps eyebrow (*"CHART 1 · PICKER
   TARGET"*), a muted meta line (*"3 series · 1 group"*), the legend inline (colour stroke + name + unit), and the card's
   own actions at the end of the head (*Synced*, *Reset Zoom*).
3. **A flight-mode band** across the top of the chart (*STABILIZE*), and a dashed cursor with a dot where it meets each
   series; a dashed horizontal reference line.
4. **A field picker**: a filter field, quick group chips (*Attitude, Rate Tuning, Vibration, GPS, Battery …*), then the
   message list with a colour dot per message and its count right-aligned and muted; the selected one tinted.
5. **Health as tinted cards**: one card per check, background and border tinted by its state (fail red, warning
   amber, info blue, pass green), a title with an icon and a state word, one bold sentence, a muted detail line, and
   its next actions (*View Data*); above them a summary: file, chips *1 failed · 1 warning · 4 passed*, and a row of
   four numbers (label small and muted over the value).
6. **Instrument tiles**: a big number with a small unit (*59.2 V*), progress bars, label / value rows with the values
   end-aligned; an attitude indicator and a data box over the map; a status strip of tabular numbers (HDG ALT SPD …).
7. **Density without clutter**: a narrow icon sidebar, small text (≈ 12–13 px), generous card gaps, few borders inside
   cards; pills with a status dot in the top bar; a thin console strip at the bottom.

Not found / not confirmed: the chart library (not named in the README or the root `package.json`), fonts and exact
colour values, spacing, motion, empty states. Nothing in this plan relies on them.

### 3.3 Three other tools – what each does well

Only what the sources read this session say (PX4's log-analysis page <https://docs.px4.io/main/en/log/flight_log_analysis>,
the ArduPilot forum's *Log inspection with PlotJuggler* <https://discuss.ardupilot.org/t/log-inspection-with-plotjuggler/122216>,
ArduPilot's UAV Log Viewer page <https://ardupilot.org/copter/docs/common-uavlogviewer.html>); nothing beyond them is claimed.

- **PlotJuggler**: plots arranged in tabs or windows and saved as a *layout* reused on other logs; new series made with
  Lua; .ulg, .csv, .mcap and live ROS topics. *We have the same* (templates, formulas / Python operations, the same
  formats); its weak point named on the forum – custom series not carried to another log – we already handle (*Copy the
  work to another file*, templates with formulas).
- **Foxglove**: replay a flight and *seek through the timeline* across every panel; per the PX4 page, automatic detection of
  common problems (high vibration, GPS degradation) and AI-assisted triage. *We have* the replay / timeline and the
  health check; an AI assistant is out of scope (offline app).
- **UAV Log Viewer**: in the browser, plots that can be manipulated, the flight re-flown in 3D. *We have both.*

What they suggest for this redesign is presentation rather than missing features: one timeline that visibly drives every
view (B5), and problems surfaced as findings at a glance (A4, D7). A raw-message inspector beside the plots (a common
feature of such tools, not checked against a source here) is noted for a later round – not in this plan.

## 4. Sweeps as one workspace

### 4.1 What a study is (one model)

**A study = a set of tables + (optionally) what they share.**

```
Study
  name, path (the file it was opened from / saved to), kind: "single" | "study"
  tables[]: { id, name, source: file | glob paths | merged(parts) | rows, rounds?: { k, path, runs }[] ,
              columns' roles + scales, question (goal, conditions, derived…), view }      ← today's StudyTable + Study
  common?: { shared params, combine, search, next, launcher, demo, history }               ← today's .svstudy.json
  active: { table id, round (k | "all") } | "common" | "about"
  answer per table (as today), common answer (ranking), loop / demo progress
  history: ONE undo stack for the whole study
```

- **One store.** `useSweeps` stays the area's store; `useStudyPanel`'s state becomes its `common` part (the `editStudy /
  undoStudy` functions become store actions writing through the same history). The `Snap` gets an optional `common`
  (the study copy, as `studyStore` already keeps whole copies) – Ctrl+Z / Y always undo the last change, wherever it was.
- **Roles, one vocabulary in the UI** (the single table's, as users know it): `param` (with a *shared* / *local* mark
  when the study has a common part), `hold` (= `scenario`), `output`, `id`, `ignore`. Mapping in one function each way
  (`studyRoles.ts`), tested with Vitest both ways on the three examples.
- **A study table's goal** (`constraints` + `objective` + `aggregate`) prefills the table's question when it is opened:
  `a < x and b < y` → two conditions; `objective` → the goal; an expression that is not `column op value` becomes a
  derived column `ok_<n> = <expr>` with the condition `ok_<n> == 1` (the formula whitelist evaluates both). Whether an
  edit in the table writes back into the study is decision 3.

### 4.2 Files and old files

- `.svstudy.json` **is the study file** (the engine's contract: CLI, schema, launcher, loop, demo). New optional key
  `workspace` (kept by `study.py` as `extra` today; added to `study.schema.json` as optional): per table id its roles
  as the UI set them, question, view; extra UI tables (merged, rows handed over) with their recipes; the active place.
  Old `.svstudy.json` files have no `workspace` – they open with the questions prefilled from the study (§4.1).
- `.svsweep` (version 1) **keeps opening** as a study with `kind: "single"` and its tables (no `common`) and **saves as
  `.svsweep`** while it has no common part – nothing changes for a one-table user. Adding shared parameters / a second
  system offers *Save as study (.svstudy.json)…*; the `.svsweep` is left as it was.
- `sweep_autosave.json` (the open studies, reopened at start): each entry may carry `common` / its path (optional field).
- No migration is needed (both additive); tests open every example and a 1.27 copy of each format.

### 4.3 The layout – three options

| | A. Navigator + table + loop column (recommended) | B. Tabs: Tables · Common · Loop | C. Two panes side by side |
|---|---|---|---|
| How | left: the study's tree (Together / Tables with rounds / Merged); middle: the chosen table's 4 steps, or Common parameters, or About; right (collapsible): the loop, the best shared values, convergence | one bar of tabs under the area bar; the Tables tab = today's single table with a table picker | Common parameters left half, one table right half |
| Demo walkthrough | every step on one screen; the loop stays visible | the round's table is one tab away; the loop is out of sight while on a table | both visible, each half too narrow at 1440 px (the parallel plot needs ≥ 700 px) |
| One place per control | yes: tables only in the navigator (today's Data-step list moves there), loop controls only in the right column | the table picker duplicates the Data step's list | the two panes repeat Save / Undo |
| Cost / risk | biggest UI change; e2e selectors of the Data step's table list change | smallest; keeps the "two apps" feeling the owner named | medium; cramped |
| 1M runs | unchanged (the middle is today's code); the navigator shows counts the server already has | unchanged | two plots at once – twice the drawing |

**Recommendation: A.** It answers the owner's words ("on the same screen") directly, makes the rounds first-class, and
removes duplicates (the Data step's *Tables in this study* list moves into the navigator; *Continue with* becomes a
click there; merge stays in the Data step as *Merge…*). Mock-up: `docs/dev/mockups/sweeps.html`
(`sweeps_dark_en.webp`, `sweeps_light_he.webp`).

What each part of today moves to:
- `SweepsBar` tabs of open studies → the top bar keeps one study pill per open study (switch / close); Open ▾ (table,
  folder, `.svsweep`, `.svstudy.json`, new study) – one menu; Study ▾ / Clear ▾ / Follow / Refresh – into the navigator's
  head (study) and the crumb (table: Follow / Refresh belong to a file table).
- `StepNav` → under the crumb, unchanged in function. Data step's table list → navigator. `StudyPanel` editor
  (tables / roles / constraints / shared / combine / search) → *Common parameters* centre view (left editor, right
  ranking, as now); `LoopSection` + `ConvergenceChart` + the demo's strip → right column; `DemoView`'s explanation →
  the *About this study* centre view (the demo opens on it the first time). `SpaceView` → Common parameters.
- New backend: `GET /api/sweeps/study/tables?study_path=` – for each table its files grouped by round (`round_(\d+)` in
  the path) with rows (counted once, cached by mtime), the demo's work folder for a demo study; polled with the loop's
  progress so a new round appears as **new** in the navigator.
