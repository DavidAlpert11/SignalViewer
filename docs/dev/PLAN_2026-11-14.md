## 0. In one page

- **Revised 2026-11-14 after the owner's first answer** (his words, translated): *"Sometimes it is used only to load
  the files after a run – and then maybe continue to another session. Sometimes only to start the run, when there may
  be no tables at all. One area must support these: an option to open something new and set things up, and if a
  results table is loaded, continue from there. There are many duplicates between the two modes of Sweeps."* And on
  ArduDeck: *"Not to take everything there, but to review its design ideas, check what is better with us and what is
  better with them, and propose a new design idea accordingly."* §3.2 and §4 are rewritten for this.
- **Sweeps (the main problem).** Today the area shows *either* the single-table study (`StudyView`, store `useSweeps`,
  file `.svsweep`) *or* Common parameters / the loop / the demo (`StudyPanel`, store `useStudyPanel`, file
  `.svstudy.json`) – two stores, two files, two Undo histories, and fourteen things done twice (§4.2). A study cannot
  start from nothing except the demo (the start grid is the demo's own field). The tables the loop writes are never
  offered to the single-table tools.
  **Recommendation (§4):** **one study, whatever the starting point.** *New study* has two ways in – *I have results*
  (a table, a folder, a saved study: the set-up is filled from the columns) and *Start from nothing* (parameters with
  ranges, scenarios, outputs and goal, how to run: round 1 is a start grid). Both land in the same workspace: a left
  navigator (Set up · Tables with their rounds · Together, when there are two systems or more), the chosen part in the
  middle (the set-up, a table's four steps, the common ranking), the next round / the loop in a right column. Save, close,
  open tomorrow and continue. Each duplicate keeps one home (§4.2).
- **ArduDeck, both ways.** Design (§3.2: where we are better, where they are) and capabilities (§3.3: what they have that
  matters for analysis, what we have that they do not show). From the design comparison our own idea – **"a quiet frame,
  the data speaks"**: neutral chrome, every surface a card with the same head, the verdict first, numbers as instruments,
  help on demand instead of on the canvas, time as the spine (§3.4, §5). From the capabilities, seven optional additions
  (F1–F7: a log's parameters and the diff of two logs, a messages view, statistics of the visible window, live
  instruments, a height profile, the wind along the track, pop-out windows) in a Phase F after the redesign.
- **Not only ArduPilot (§3.6).** Every idea taken from ArduDeck is made format-neutral: it reads what the data has
  (columns, structs, topics, state signals, limits, quality) and a *profile* – a built-in or the user's template – adds
  the domain's content (ArduPilot, a car, a test bench, a simulation). Health becomes one *Checks* view (limits + data
  quality + a log's health), the summary row extends the existing *run at a glance* strip, F1 / F3 / F4 / F6 become
  *The file*, *Parameters of a run*, live instruments for any source, vectors along any path.
- **The map (§3.7).** Online streets / satellite / topo already exist but hide in a select; proposed: a background
  picker with thumbnails, *Satellite + roads*, *Keep this area offline…* (only from sources whose terms allow it), *My
  maps* (MBTiles, the organisation's tile server); Offline stays the default.
- **Every feature stays.** §2.2 is the acceptance checklist (every capability and where it is today → where it goes).
- **Order of work:** five lanes in parallel (Look · Sweeps · Plots and the frame · Map · Analysis and new capabilities),
  each owning its files, one sync point (the component classes), then a final lane: docs, the full checks, the version
  (§7.0). Tests per task only where relevant; the full e2e suite once, before the version update. One agent alone follows
  A → C → B → M → D → E → F.

### 3.1 ArduDeck – what could be confirmed

Sources (read 2026-11-14): the site <https://ardudeck.com/>, its screenshots page <https://ardudeck.com/screenshots/>,
the blog post <https://ardudeck.com/blog/introducing-ardudeck-ground-control-station/>, the repository

<https://discuss.ardupilot.org/t/welcome-to-ardudeck-a-modern-ground-control-station-for-ardupilot/144390>, ArduPilot's

directly: `flight_log_explorer.jpg`, `telemetry_tactical.jpg`, `flight_log_health.jpg` (under
`https://ardudeck.com/images/`; not copied into this repository).

What the pages say: a ground control station for ArduPilot, iNav and Betaflight (Electron, React 18, TypeScript,
Vite, Zustand; *"The UI is Tailwind CSS, dark theme"*); a dashboard of *"IDE-style panels with saveable layouts"*; 30+
map instruments in *"analog, numeric and compact variants"*; a Log Explorer with *"multi-chart plotting … independent
y-axes, zoom/pan, windowed min/avg/max stats, and synchronized cursors across charts, map, and 3D flight path"*; health
reports with pass / warn / fail checks; a field picker. Beta (versions on the pages disagree: 0.1.x / "Beta 1.2").

What the screenshots show (observed, described in words):
1. **A darker, cooler canvas** (near-black navy) with panels one step lighter and 1 px borders; the plots' backgrounds
   are the darkest surface, so saturated series stand out. A light theme exists for the telemetry view.
2. **Chart cards with a head of their own**: a tab-like title with ×, a small-caps eyebrow (*"CHART 1 · PICKER
   TARGET"*), a muted meta line (*"3 series · 1 group"*), the legend inline (colour stroke + name + unit), and the card's
   own actions at the end of the head (*Synced*, *Reset Zoom*).
3. **A flight-mode band** across the top of the chart (*STABILIZE*), and a dashed cursor with a dot where it meets each
   series; a dashed horizontal reference line.
4. **A field picker**: a filter field, quick group chips (*Attitude, Rate Tuning, Vibration, GPS, Battery …*), then the
   message list with a colour dot per message and its count right-aligned and muted; the selected one tinted.
5. **Health as tinted cards**: one card per check, background and border tinted by its state (fail red, warning
   amber, info blue, pass green), a title with an icon and a state word, one bold sentence, a muted detail line, and
   its next actions (*View Data*); above them a summary: file, chips *1 failed · 1 warning · 4 passed*, and a row of
   four numbers (label small and muted over the value).
6. **Instrument tiles**: a big number with a small unit (*59.2 V*), progress bars, label / value rows with the values
   end-aligned; an attitude indicator and a data box over the map; a status strip of tabular numbers (HDG ALT SPD …).
7. **Density without clutter**: a narrow icon sidebar, small text (≈ 12–13 px), generous card gaps, few borders inside
   cards; pills with a status dot in the top bar; a thin console strip at the bottom.

Not found / not confirmed: the chart library (not named in the README or the root `package.json`), fonts and exact
colour values, spacing, motion, empty states. Nothing in this plan relies on them.

### 3.4 The new design idea – "a quiet frame, the data speaks"

Six rules. Each rule takes a strength from one side and keeps ours where we are better:

1. **The frame is quiet.** Chrome is neutral grey-blue on a deeper canvas. The **UI accent is no longer the trace amber**:
   the cursor and time keep amber (it is *measurement*), and the selection, the active plot and the primary button get a
   neutral bright ink with a thin ring. The 2nd trace colour moves away from the cursor's hue (the Okabe–Ito set keeps
   its order; the cursor's amber gets more yellow, or the cursor gets a white / ink line with an amber flag – decided in A1
   by a contrast and a colour-vision check). Status colours (ok / warn / danger / info) appear **only** on verdicts.
2. **Every surface is a card with the same head**: eyebrow · title · one muted meta line · at most two actions + ⋯.
   Plot cards, panel findings, the Sweeps set-up sections, a table in the navigator, the loop – one anatomy to learn.
   Our powerful controls stay, behind the head (the axis menu, add an object, cameras go to ⋯ / the map's glass bar).
3. **The verdict first.** Every analysis surface opens with one sentence and a tinted state: the health check, What
   changed, Compare, a Sweeps table (*12 of 45 sets hold*), the loop (*converged after 3 rounds*). We already write these
   sentences (*the process in brief*, *at a glance*); now they lead the layout, and each ends with its next action.
4. **Numbers are instruments.** IBM Plex Mono, label small and muted over the value, the unit smaller; a dot on each line
   at the cursor; values in the legend.
5. **Help on demand, never on the canvas.** Hints over a plot or the map show once (first use) and then live behind a
   `?` in the card's head; warnings like *Reduced quality* become one quiet line in the status bar.
6. **Time is the spine.** One timeline with the modes in colour drives every plot, the map, 3D and the story; the shared
   MODE lane stays above the plots (ours), with a thin echo of it in each card (theirs).

Kept as they are, because they are better with us: the named rail, the sparklines in the tree, two cursors and the
Inspector, the shared lanes, both themes AA, Hebrew RTL, the welcome's demos. Not taken: an icon-only sidebar, docking /
pop-out windows (a later decision), anything of their branding, icons or exact screens.

The mock-ups (§5.6) show rules 2–6; rule 1's accent split is drawn in them as today's amber for the active plot and is
the first decision of Phase A (§8, decision 4).

Only what the sources read this session say (PX4's log-analysis page <https://docs.px4.io/main/en/log/flight_log_analysis>,
the ArduPilot forum's *Log inspection with PlotJuggler* <https://discuss.ardupilot.org/t/log-inspection-with-plotjuggler/122216>,
ArduPilot's UAV Log Viewer page <https://ardupilot.org/copter/docs/common-uavlogviewer.html>); nothing beyond them is claimed.

- **PlotJuggler**: plots arranged in tabs or windows and saved as a *layout* reused on other logs; new series made with
  Lua; .ulg, .csv, .mcap and live ROS topics. *We have the same* (templates, formulas / Python operations, the same
  formats); its weak point named on the forum – custom series not carried to another log – we already handle (*Copy the

- **Foxglove**: replay a flight and *seek through the timeline* across every panel; per the PX4 page, automatic detection of
  common problems (high vibration, GPS degradation) and AI-assisted triage. *We have* the replay / timeline and the
  health check; an AI assistant is out of scope (offline app).
- **UAV Log Viewer**: in the browser, plots that can be manipulated, the flight re-flown in 3D. *We have both.*

What they suggest for this redesign is presentation rather than missing features: one timeline that visibly drives every
view (B5), and problems surfaced as findings at a glance (A4, D7). A raw-message inspector beside the plots (a common
feature of such tools, not checked against a source here) is noted for a later round – not in this plan.

### 3.6 Signal Viewer is an analysis tool for any time signals – the ArduDeck ideas made general

The owner (2026-11-14): *"We are an analysis tool, not necessarily for ArduPilot – what else must be done in the design
context of ArduDeck?"* ArduDeck is a ground station for one family of autopilots: its screens know every message name
in advance. Signal Viewer's users bring ArduPilot / MAVLink / PX4 logs, but also MATLAB / Simulink `.mat` and Python
results, test-bench and vehicle CSV / Parquet / HDF5 (the car-runs example), ROS 2 `.mcap`. So:

**The rule.** No part of the design may depend on a file format. Each idea takes its content **from what the data has**;
where the format is known (an ArduPilot log), a richer content is offered by a **profile** – and a profile is not a new
mechanism: it is a built-in template (they already carry views, conditions and limits), extended with its *at a glance*
numbers and its chips. A user's own template is a profile too (a test bench, a car, a simulation). One way to do a thing.

What already is general (checked in the code): the state lanes (any text / few-valued signal, *Always as a state*);
*the run at a glance* strip above the plots (the run's phase, length, automatic flags); the data quality of any file
(`svcore/quality.py`, `QualityDialog`); limits per signal (`svcore/limits.py`, templates; `signalviewer-cli check` with a
`checks.json` – `examples/checks.json` is the car's); *Runs × conditions* (a run's parameters from constant signals and
file names); the file tags A / B / C; *what does not apply is hidden* (no Map / 3D without positions). The wording is
mostly neutral (a few dozen strings say *flight* where they mean *recording*).

| ArduDeck idea | Made general (any data) | A flight log adds (profile) | Simulation / bench / car / ROS |
|---|---|---|---|
| A summary row of numbers | **extend the existing *run at a glance* strip** (not a new strip): length, rate, the phase row, then up to four numbers – from the profile, or pinned by the user (a statistic from the Inspector / Analysis: *pin to at a glance*) | max altitude, distance, battery used, flight time per mode | max / final of the outputs the template names (final error, max overshoot, max engine temperature, time in CRUISE) |
| Health cards, pass / warn / fail | **one *Checks* view** (one home; today three places): the user's **limits** (Inspector, templates, `checks.json`), the file's **data quality** (gaps, NaN, flat, spikes, time jumps), and the log's **health check** when there is one – the same tinted cards, the counts in the strip | the health check's findings (vibration, EKF, GPS, battery, errors) | limits from the template or a `checks.json` (as the CLI reads) – a test bench's pass / fail on screen, not only in CI |
| Quick group chips over the field list | chips from **the file's own structure**: column prefixes (`Engine_*`, `imu.`), MAT structs, log message groups, MCAP topics; **+ pin a search** (kept with the template); *Has limits*, *States*, *On a plot* | ATT, RATE, VIBE, GPS, BAT… and the built-in views' topics (Attitude, Vibration…) | `Engine`, `Speed`, the Simulink buses, the ROS topics |
| A mode band in the chart | any **state signal** (already general) | MODE, flight mode | DriveMode, gear, the simulation's phase, a test step number |
| A message inspector (F1) | ***The file*** in the Log panel's place for any file: its groups / topics / structs, each column's rate, samples, unit, time base, gaps – and its values at the cursor; a click plots | message types, their rates, MSG text | MAT structs and their fields, a CSV's columns, MCAP topics and their rates |
| Parameters (F3) | ***Parameters of a run***, one source for every format, and **two runs compared** (only what differs) – merges with *Runs × conditions* (it reads the same thing) | the log's parameters (PARM), changed in flight | MAT scalar variables and parameter structs, constant columns, numbers in the file name |
| Live instruments (F4) | big numbers + the attitude indicator + the map for **any live source** (MAVLink, *Send data from Python*, a file being written and followed) | ALT, SPD, HDG, battery, GPS fix, mode | any signals chosen (tiles from the template) |
| Altitude profile (F5) | the **height and ground along the path** for any file with positions (the one *is this a position* rule); hidden otherwise | GPS / EKF position | a simulation's trajectory with lat / lon / alt; nothing for the car runs |
| Wind on the map (F6) | **vectors along the path**: any two signals (N / E, or X / Y) as arrows on the track – wind, velocity, force, error | XKF2 VWN / VWE offered by itself | a simulation's wind or force vectors, a vehicle's slip |
| Fleet of vehicles | (later, a decision) the Fleet as **a collection of runs of any format**: the numbers from the Checks view and *at a glance* over many files, the trend and the limit | today's Fleet (flight logs) | many test-bench runs, many simulation batches |

**And in the look itself:**
- **Words**: the chrome says *recording / run / signal*; domain words (*flight*, *vehicle*, *arm*) only inside a profile's
  content and the examples. An audit of the generic i18n files (a few dozen strings) → D13.
- **Icons**: neutral (data, chart, check, state, map) – no aircraft in the frame; the vehicle icon only on a map object.
- **Units and time**: any unit (from the file or set), time in s / ms / samples / a timestamp, never assumed GPS / UTC.
- **The welcome** keeps a demo per domain (drone, car runs, a model against its flight, sweeps, fleet) and gains a
  **test-bench example** (a Parquet or HDF5 run with a `checks.json`: the Checks view and *at a glance* outside aviation) → E4.
- **Mock-up** `recordings-any.html`: the same screen as `recordings.html` on the three car runs – the strip, the checks'
  counts, the chips from the columns, DriveMode as the band, no Map / 3D (positions absent).

## 4. Sweeps as one study, whatever the starting point

### 4.1 How the owner's users work (the two flows, and continuing)

1. **Results first.** The runs were made elsewhere; the user loads the results (a table, a folder of tables, a saved
   study) to find which settings hold and which is best – and may then want *more* runs (next runs, exported or run by
   the app), today or in another session.
2. **Runs first.** There are no tables yet. The user says what varies (parameters and ranges), in which scenarios, what
   the program writes and what is good, and how one run is started – and the app runs round 1, then aims each next round.
3. **Continue.** Either flow is saved as one study and opened again later: the tables (and new rounds) are read again,
   the set-up and the questions are as they were, the loop resumes from its history.

Today flow 1 is the single-table study, flow 2 exists only for the demo, and the step from 1 to 2 (from results to
running more) crosses into the other mode.

### 4.3 One study: Set up · Tables · Together · Run

```
Study  (one file, one Undo, one Save)
  Set up      what varies (parameters: min / max / step / values / log; constraints between them)
              scenarios (per system: columns and their values)
              outputs and goal (= the Goal step of each table)
              how to run (this PC / a farm launcher: command, parameters file template, where results land)
  Tables      per system: its files (loaded or written by the rounds), its rounds, its four steps
              (Data · Columns · Goal · Results + Next runs, report) – today's single-table tools, unchanged inside
              merged tables (a new table from others)
  Together    (only with two systems or more) the shared parameters, the ranking, the space – today's Common parameters
  Run         (right column) round k: what it will run (sets × scenarios = runs, the full grid for scale), what is
              missing, Run / Only write the files / Next round / Until converged / Stop; progress and convergence
```

- **I have results →** the table opens; Set up is *filled from the columns* (params = what varies, their min / max / the
  values seen; holds = scenarios; outputs) and stays editable; Results answers at once. *Next runs* proposes; with a
  command in *How to run* the Run column can run them; without one, *Export…* as today.
- **Start from nothing →** Set up is typed (mock-up `sweeps-start.html`); *Run round 1* is enabled when the parameters,
  scenarios, an output to rank by and a command are there (the column says what is missing). Round 1 = a start grid
  (per-parameter counts, e.g. 4 × 4 × 3) × the scenarios. Its results appear under Tables as *Round 1*.
- **Continue →** Save writes the study; opening it lists every round found on disk (new files since: marked *new*).
- **The demo** is an example study of this kind (Start from nothing, with `sim.py` as its command); its explanation
  becomes the study's *About* page, the reference grid stays its own extra.

Engine changes (small, no new maths): the start grid becomes any study's (`start: {grid: {param: n}, scenarios:
{table: {column: [values]}}}`; the demo's `demo.start_grid` / `demo.scenarios` keep being read as before – the loop
reads `start` first, then `demo`); the set-up's ranges are today's `search.params`; *How to run* is today's `launcher`.

### 4.4 One model, one store, one vocabulary

```
Study
  name, path, file kind ("svsweep" when opened from one and still one table without Set up / Together)
  setup:   { params (search.params), constraints (search.constraints), start, launcher, next }
  tables[]: { id, name, source: files | globs | merged(parts) | rows, rounds[]: { k, path, runs, new },
              shared: true|false (a system of the study, or a merged / side table),
              columns' roles + scales, question (goal, conditions, derived…), view, answer }
  together?: { shared params, combine, ranking, space }      (present with ≥ 2 systems)
  run:     { history (the study's rounds), progress }
  history: ONE undo stack
```

- **One store.** `useSweeps` stays; `useStudyPanel` is folded into it (its `editStudy / undoStudy` become store actions
  through the same history; `Snap` gets the set-up / together parts – small JSON, as `studyStore` keeps today).
- **One vocabulary** in the UI: `param` (*shared / local* with ≥ 2 systems), `hold` (= scenario), `output`, `id`,
  `ignore`; `studyRoles.ts` maps both ways (Vitest on the three examples).
- **The Goal step writes the study.** Conditions `column op value` with *in every combination* ↔ `constraints`
  (`a < x and b < y`) + `aggregate: worst`; the goal column and direction ↔ `objective`. What the engine of Together
  cannot express (k of n combinations, robust to, several goals compared, weights) stays the table's own and is marked
  *this table only* in the Goal step; Together uses the rest. One editor, no second one to keep in step.

### 4.5 Files and old files

- **One study file: `.svstudy.json`** (the engine's contract: CLI, schema, launcher, loop, demo) with an optional
  `workspace` key for what only the UI needs (per table: roles as set, the full question, the view; merged tables'
  recipes; the place last shown). `svcore/study.py` keeps unknown keys already (`extra`); the schema gets it as optional.
- **`.svsweep` keeps opening** (a study with one table, Set up filled from its columns) and, while the study stays one
  table without Set up / Together, **Save writes `.svsweep`** – a results-only user sees no change. Adding a command, a
  start grid or a second system makes Save offer `.svstudy.json` (*Save as study…*); the old file is left as it was.
- `sweep_autosave.json` (open studies reopened at start): each entry may carry the study path / set-up (optional).
- Old files of both kinds open unchanged (additive fields only); tests open every example and a 1.27 copy of each.
