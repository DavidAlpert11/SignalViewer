## 2. Sweeps - the table's own tools (one place: the Columns step)

The principle (one way to do a thing): the table is never changed on disk; every edit is a step of its recipe
(saved in the `.svsweep` / study file, undone with the area's one Ctrl+Z, listed in *Where it comes from*), and
**Export the table** writes the result as a new file when wanted.

2a. **Columns with conditions** - the formula grows into the Recordings formula's language, the same AST whitelist
   (one evaluator for both where possible, `svcore/formula.py`), no `eval`:
   - `if(cond, a, b)` (and nested), comparisons and `and / or / not`, `between(x, lo, hi)`;
   - text columns: `== "mild"`, `in ("mild", "strong")`, `contains(name, "B")`, text results (`if(wind > 8,
     "high", "low")` -> a text column, usable as a scenario);
   - `bins(x, [0, 5, 10])` -> categories; `rank(x)`, `pct(x)` (percentile in the table); `lookup` is not needed;
   - per set (exists): min / max / mean / worst over its runs, now also `count(cond)` and `share(cond)` ("in how
     many scenarios it held").
   The editor keeps its completion and live value of the first run; a *Template* of the table carries the formulas.
2b. **Edit the table** (a panel of the Columns step, *Table tools*): drop columns (and *Drop every Not used* in one
   click), rename a column (the display name; the file's name kept for templates), its unit, keep / drop rows by a
   condition (`crashed == 1` out - the Keep / Exclude of the plot already does it for the view: here it is part of
   the table), fix one value (a cell override, listed, undone). Each one a recipe step.
2c. **Export the table** (Data step, the table's ⋯ menu): CSV / Parquet / Excel of the table as edited - exists for
   CSV; Parquet and Excel added, and *with the recipe* (a small JSON beside it) so it can be read again.

## 3. From recordings to a Sweeps table - "Summarize runs" (the heavy part solved in the backend)

A Sweeps table is a row per run. Engineers often have the runs as recordings (sim outputs, test flights). One
mechanism, two entry points:

- **The summary** (`svcore/summary.py`, new): a list of *measures*, each a name, a signal (by name, as templates
  match signals) and what to take: max / min / mean / RMS / final / first / at time t / at an event (a condition's
  first stretch) / time to reach a value / duration a condition holds / overshoot / settling time (the step-response
  numbers that exist in Analysis). Plus *parameters* of the run: from its metadata, from its file / folder name by
  a pattern (`kp_{kp}_wind_{wind}.csv` -> two columns - no regex for the user), or a constant per folder.
- **Where the runs come from**: (a) the runs open now - instant; (b) **a folder** - read one file at a time in the
  backend in a Store of its own (as the Fleet does), never into the UI: memory stays that of one file; progress,
  Cancel, and a cache per file (path + size + mtime) so adding files or a measure reads only what is new.
- **Entry points**: Sweeps' Data step -> *Add table ▾ -> From recordings…* (the main one: the user is in Sweeps);
  Recordings' Runs matrix -> *Open as a Sweeps table* (its rows are the open runs, its columns become measures).
  A Command-palette entry, and `python cli.py summarize --measures m.json logs/ -o table.csv` for the farm.
- **The table remembers where it came from**: each row keeps its file; in Sweeps, a set's details offer *Open this
  run in Recordings* (at the measure's moment). The measures are saved (a *summary template*, JSON) - re-run on a
  new folder in one click, and next rounds' recordings summarized the same way (the loop can read recordings, not
  only result rows: `launcher.results.summary`).
- Heavy? Measured first (a folder of 200 ArduPilot logs, 50 MB each): time and peak memory per file; reading only
  the signals the measures need (the readers that can - CSV columns, Parquet, HDF5, MAT variables - read only
  those). Target: memory flat (one file), the UI responsive.

## 4. Recordings - Export a subset ("a sub-recording")

One dialog, *Export recording…* (TopBar's Save ▾ - workspace / file actions; Ctrl+K), for one run or every open
run (one file each):

- **Signals**: the ones in the plots on screen / chosen (the signal picker) / a template's / all; derived signals
  as values; names as in the app (or as in the file).
- **Time**: all / what the plots show / between the cursors / **only where a condition holds** (Investigate's
  stretches, with a margin; as separate files or one file with a gap column).
- **Rate**: as recorded (each signal's own time - formats that keep groups: HDF5, MAT, Parquet per rate) or **one
  time base at a chosen rate** (Hz, or "the rate of signal X"): interpolated linearly, states and integers held
  (previous value), with an anti-alias low-pass when the rate goes down (said in the dialog, can be turned off).
- **Format**: CSV, Parquet, MATLAB .mat, HDF5 (the writers we have; any new dependency noted with its reason);
  units in the header / attributes; time from 0 or as recorded; a small JSON sidecar of what was taken.
- **Round trip**: the exported file opens in the app with the same values (an e2e test per format) - and the
  same export from the command line (`cli.py export --signals ... --rate 50 --format parquet`).
- It replaces the scattered exports of signals (Export CSV of a plot stays as the quick one, implemented by this).

## 5. More ideas in the same spirit (proposed, not promised)

- **Parameters from names** everywhere a folder is read (Sweeps' folder, Fleet, Summarize) - the same pattern box.
- **A run's health as a column**: the health check's verdict / findings counts as measures (bad runs filtered out
  before ranking).
- **Units travel**: a recording's units become the Sweeps column's unit (axes, report).
- **Sweeps -> Recordings and back**: from a set, *Overlay its runs* in Recordings (the runs of the best set and
  of a failing one on the same plot).
- **One "measures" library**: the measures of Summarize, the Runs matrix and Fleet's trends are the same objects
  (a step-response measure defined once is a Fleet trend, a Sweeps column and a report number).
- **Big folders**: the summary's cache is also what makes a re-opened study fast (no re-reading).
