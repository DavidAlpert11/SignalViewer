# Plan 2026-11-16 - main (1.28.0) is not stable: Out of Memory, the 3D map's render error, slow maps

The owner's report (Windows, a real graphics card): the browser tab dies with *Out of Memory*; the 3D map shows
Cesium's *"An error occurred while rendering ... Fragment shader failed to compile"*; maps open slowly; the e2e suite
died after 20 tests with `MemoryError`. v1.26.0 was fine.

## 1. How it was measured

`tools/measure_maps.py` (kept for the owner): opens the examples with a map (flight, ardupilot, twoFlights,
simVsFlight) one after another, clicks every camera and every tab, closes the files (the welcome screen: every plot
unmounted) and opens the next - 5 cycles = 20 openings - and after each closing records the JS heap (after a forced
GC), the WebGL contexts still alive in the page, the Cesium widgets alive, the browser's memory (every process), the
server's memory and the time from the click to a drawn map. *Light* = software WebGL (the cloud machine: the app's
light mode); *full* = the same, with a hardware renderer reported (the app's full mode: sky, lighting, MSAA 4,
shadows) - the path the owner's PC takes. 1440x900, Chromium 1243, 4 cores, no GPU.

## 2. Findings

(08f7fbd, 1.28 before the one-map templates, 12 openings: two views per opening, like v1.26.0.)

**F1 - every closed 3D map stays alive with its whole WebGL context (the Out of Memory).** `CesiumWidget.destroy()`
runs on unmount, but the context is never released: Cesium keeps the terrain grid's index buffers in a *static*
cache (`TerrainProvider.getRegularGrid…Indices(65, 65).indexBuffers[context.id]`, `GlobeSurfaceTile`), and the
destroyed buffer keeps `_gl` -> the context -> the canvas, its framebuffers, MSAA buffers and shadow maps (found with
a heap snapshot: `Window -> Cesium module -> cache[65][65].indices.indexBuffers[<id>]._gl -> WebGL2RenderingContext`).
Every opening of a map leaves one context; the browser drops the oldest only at 16 ("Too many active WebGL contexts").
The leak is old (v1.26.0 leaks two per opening), but **1.28 made each leaked context about twice as heavy** (one
map filling the stage instead of two smaller views: ~49 MB kept per opening instead of ~22 MB in software; on a
graphics card the full mode's MSAA 4 and 2048² shadow maps scale with the canvas). On a GPU that memory is video
memory, and with 16 of them held a real PC runs out - the tab dies, and a shader compiled on a starved / lost
context fails with an empty log: *"Fragment shader failed to compile"* (WebGL reports a failed compile when the
context is lost). Also: `window.__svGlobe` (for the tests) kept the last closed view.

**F2 - a failed render leaves Cesium's dead dialog.** `showRenderLoopErrors` was on and nothing listened to
`scene.renderError`: the view stopped for good with the dialog, no fallback.

**F3 - small leaks in the view:** the label-placement listener (W9, `scene.postRender`) was added on every rebuild of
the models and never removed; the view's own `ScreenSpaceEventHandler` (clicks, with listeners on the document)
was never destroyed.

**Not the cause** (measured): the one-map templates (29e8d2c / 7a4365a) - one view per opening instead of two, and
faster to draw; the terrain provider made again on a new terrain version (P5) - the old provider is not held
(one provider per view in the snapshot); the server - its memory grows ~2.4 MB per opening in every version
(caches), unchanged by 1.28 (followed up below).

**Slow maps:** in these measurements main draws *faster* than v1.26.0 (one view instead of two). The slowness the
owner sees is most likely the same memory pressure (a GPU with 16 held contexts swaps / evicts). To be confirmed
with the owner's numbers (below).

## 3. The fix (done - small, in `Globe3D.tsx`)

1. On unmount: destroy the click handler, destroy the widget, **remove the destroyed context's entries from Cesium's
   index-buffer cache, and lose the context at once** (`WEBGL_lose_context`), canvas to 0x0; clear `__svGlobe` if
   it is this view. -> 0 contexts alive after closing; the browser's memory flat over 20 openings (table).
2. `showRenderLoopErrors: false` + `scene.renderError`: a failed render in the full mode makes the view again in
   the **light mode** (and every view after it, until a reload); a failure in the light mode draws the **flat map**
   with its note. The error goes to the app's log (`~/.signalviewer/logs`, Help > Copy error details).
3. The W9 listener removed with the models.
